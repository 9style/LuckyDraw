## 一、概述

一个纯前端 H5 互动页：员工填写 4 个字段，摇签筒，得到一份「职场运势」结果，可生成分享海报。摊主线下收款，口头告知当日口令，用户输入口令解锁完整结果。

**本设计对 PRD 的偏离与补充**共 5 处，集中在第四章「与 PRD 的差异」列出，均已在设计评审中确认。

---

## 二、目标与非目标

### 目标
1. 现场主链路（填表 → 动画 → 结果 → 海报）在弱网、断网下可用
2. 结果「准」且有分享欲 —— 靠部门梗、身份标签、自洽的分数与签文
3. 合规零风险 —— 无数据上报、无后端、无支付接口
4. 运营可直接改文案与权重，不改代码

### 非目标（明确不做）
- 后端服务、数据库、用户账号
- 支付接口、订单、验票（口令机制替代）
- 微信 JS-SDK 自定义分享卡片（无公众号资质，降级为用户长按海报自行转发）
- 埋点 SDK、第三方统计（仅本地计数，见 5.3）
- 多语言、多活动复用、后台管理界面

## 三、技术栈与工程结构

### 技术栈
| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Vue 3 + Vite | 结果页 7 个模块需要组件化；构建产物静态托管 |
| 路由 | **无**（单页状态机） | 姓名/部门不进 URL（合规）；现场无人使用后退键 |
| 状态 | `reactive` + `sessionStorage` 持久化 | 不引入 Pinia，状态量小 |
| 二维码 | `qrcode-generator` | ~10KB，输出矩阵供 Canvas 自绘，无 DOM 依赖 |
| 海报 | **纯 Canvas 2D 自绘** | 见第十章 |
| 文字校验 | 自写 `validators.js` | 无第三方依赖 |
| 测试 | Vitest | 与 Vite 同源，零配置 |

**不引入**：html2canvas、vue-router、Pinia、任何 UI 组件库、任何字体文件、任何网络请求。

## 四、与 PRD 的差异（5 处，均已确认）

| # | PRD 原文 | 本设计 | 原因 |
|---|---|---|---|
| 1 | 流程含「⑤ 付款确认：展示摊主收款码 → 用户点"我付好了"」 | **删除收款码与"我付好了"**，口令输入框置于结果页 | 收款码做成立牌更合适，塞进 H5 别扭；摊主只需报口令 |
| 2 | 免费模式在**开场页**输口令 | 口令入口**只在结果页一处** | 支付环节已删，开场页入口会迫使已付费用户重填表单 |
| 3 | 打分配方：星座基础值 60~85 | 星座基础值 **45~90**，年限 **-8~+10**，部门 **-6~+8** | 按原配方最低分 44，**「危」档（0-39）永不可达**，四档文案只用到两档半 |
| 4 | 7.2 半截结果「只露出身份标签 + 一句悬念」，示例为打码的 `██████型选手` | **身份标签完整露出**，改锁四维数值、吐槽、签辞、彩蛋；签文吉凶等级露出 | 打码标签会让用户失去"好准"的瞬间，反而削弱解锁动力 |
| 5 | 5.2 提到六档（含大凶） | **只实现 6 个标签名 / 4 个概率档**：上上签、大吉、中吉、小吉、平、小凶；**不实现「大凶」** | 符合第八章"绝不真凶"红线；PRD 5.2 表格本身也只有四行、无「大凶」行 |

## 五、状态机与数据流

### 5.1 阶段

```
intro ──开始──> form ──提交──> divining ──3s──> result(locked)
                                                    │
                                          输对口令 ──┤
                                                    ↓
                                              result(unlocked) ──> poster
                                                    ↑                │
                                                    └──再算一次──────┘
```

`stage` 为单一响应式变量，取值 `intro | form | divining | result | poster`。视图间用 `<Transition>` 淡入淡出。`result` 阶段另有布尔量 `unlocked` 区分两态。

### 5.2 reading 冻结（关键设计）

**动画结束的那一刻一次性算出完整结果对象并冻结**，此后所有渲染只读该对象：

```js
reading = {
  scores:     { moYu: 72, shengZhi: 55, renMai: 81, caiYun: 63 },
  bands:      { moYu: 'ji', shengZhi: 'ping', renMai: 'daji', caiYun: 'ji' },
  avg:        67.75,
  identity:   { text: '会议隐身术大师', dept: null },
  roastTexts: ['星座吐槽', '年限吐槽'],     // 2~3 句。注意字段名是 roastTexts，不是 roasts
  deptJoke:   '部门专属梗',
  fortune:    { level: '中吉', verse: '...', yi: '...', ji: '...', explain: '...' },
  lucky:      { color: '...', number: 7, direction: '...', zodiac: '...' },
  vars:       { name: '张三', dept: '技术 / 研发', zodiac: '双子座', tenure: '入职 1-3 年' }
}
// seed 不在其中：它由 DivinationView 自行计算，并在 setReading 时附加到 store 上。
// 分工是有意的 —— buildReading 只产出内容，种子的生命周期归调用方。
```

**为什么必须冻结**：PRD 5.1 含 ±6 随机波动。若在渲染时才算分，用户每次重渲染分数都会变 —— 那是 bug 不是趣味。PRD 所说"同一输入多次算结果略有不同"指**每次重新占卜**不同，不是同一次内抖动。冻结后页面内绝对稳定，点「再算一次」才重新掷骰子。

**签的一致性**：动画中签筒弹出的那支签与结果页显示的签是同一个 `reading.fortune`。二者读同一数据源，不可能不一致。

### 5.3 会话恢复

`sessionStorage` 存 `{ profile, reading, unlocked, stage }`，页面重载时尝试恢复。

选择 `sessionStorage` 而非 `localStorage` 的理由：
- `localStorage` 永久保留 → 用户次日再扫码直接是解锁态，**白嫖漏洞**
- `sessionStorage` 关闭标签页即清空 → 每单必须重输口令
- 同一标签页内刷新不丢 → 微信 XWeb 杀后台、误触刷新、弱网重载均不丢失表单

姓名进 `sessionStorage` 不违反 PRD 第八章：仍是本地处理、不上传、不落库、关页面即清。

### 5.4 计数（`localStorage`）

`localStorage` 只存一个递增整数 `ld_count`（累计占卜次数），供现场大致了解参与量。受 `settings.json#enableCount` 开关控制。

**唯一的持久化数据是一个计数器，不含任何用户输入。** 这是有意的边界：PRD 第十三章要求"确认无任何数据上报"，一个匿名计数既满足"现场知道算了多少次"，又不触碰任何个人信息。

`localStorage` 与 `sessionStorage` 的分工不可混淆：**计数要跨会话持久，解锁态绝不能跨会话持久**（否则次日扫码即可白嫖）。

## 六、打分引擎

### 6.1 配方

```
基础分   = 星座基础值（每星座每维 45~90）
年限加成 = -8 ~ +10
部门加成 = -6 ~ +8
随机波动 = ±6（每次重新占卜时重掷）
最终分   = clamp(基础分 + 年限加成 + 部门加成 + 随机波动, 0, 100)
```

极值 **25 ~ 100**，四档等级带全部可达。期望分布约：危 3% / 平 26% / 吉 52% / 大吉 19%。

> **实测修正（Task 9 落地后）**：以上为设计时的粗估，实际不符合。10000 个画像 × 4 维（种子 20260913）实测为 **危 0.92% / 平 13.20% / 吉 54.03% / 大吉 31.85%** —— 比分位数更向高端偏斜，`危` 比预估稀有约三倍。四档仍全部可达（这是测试断言的性质），且偏斜方向与「公益活动人人笑着离开」的产品目的一致，故**接受该分布，不调权重**。调参用 `npm run simulate`，实测数据以它为准。

### 6.2 等级带

| 分数 | key | 标签 | 图标 |
|---|---|---|---|
| 0-39 | `wei` | 危 | 💀 |
| 40-59 | `ping` | 平 | 😐 |
| 60-79 | `ji` | 吉 | 👍 |
| 80-100 | `daji` | 大吉 | 🌟 |

**文案按等级带匹配**，不按具体分数 —— 只需准备 **4 维 × 4 档 = 16 个档位组合**的文案（每档可放多条轮换，实际条数见 7.5），而非 100 份。

### 6.3 配置约束（可测试）

`config/scoring.json` 中 12 星座的数值必须满足：

1. **每维跨度覆盖 45~90** —— 保证个体差异明显
2. **每个星座的四维均分互相接近（极差 ≤ 5）** —— PRD 8.4 要求"不得贬低任一星座"。某星座四维均分显著低于其他即为歧视性设计，由单元测试强制

## 七、签文与文案引擎

### 7.1 签文档位与偏置

**标签名（6 个）**：`上上签 / 大吉 / 中吉 / 小吉 / 平 / 小凶`
**不实现「大凶」** —— PRD 第八章红线。

**基准权重**（对应 PRD 5.2 的四档占比 20% / 45% / 25% / 10%）：

| 标签 | 基准权重 | 所属档 |
|---|---|---|
| 上上签 | 8 | 好签档（合计 20%） |
| 大吉 | 12 | 好签档 |
| 中吉 | 22 | 中吉小吉档（合计 45%） |
| 小吉 | 23 | 中吉小吉档 |
| 平 | 25 | 平档（25%） |
| 小凶 | 10 | 小凶档（10%） |

**偏置系数**乘在基准权重上，归一化后抽样：

| 四维均分 | 偏置系数 |
|---|---|
| ≥ 77 | 上上签 ×1.6、大吉 ×1.6、中吉 ×1.3、小吉 ×1.3、平 ×0.7、小凶 ×0.3 |
| 70-76 | 全部 ×1.0（即 PRD 基准） |
| < 70 | 上上签 ×0.6、大吉 ×0.6、中吉 ×0.8、小吉 ×0.8、平 ×1.5、小凶 ×1.5 |

偏置后归一化再抽样。均分 85 的用户小凶概率为 `3.0 / 111.0 ≈ 2.7%` —— 该反差是笑点而非矛盾。

> **阈值重标定（Task 13 审查时发现并修正）**：本节最初写的阈值是 **80 / 60**，那是错的。
> 穷尽枚举（288 画像 × 13⁴ 抖动元组 = 8,225,568 次抽取，逐维 clamp+round 后取四维平均）
> 实测四维均分的可达范围只有 **64.00 ~ 83.00**，均值 **73.21**，中位数 **73.25** ——
> 范围之所以窄，是因为 §6.3 的星座公平性把每个星座的四维和归一到恰好 280，
> 再叠加幅度有限的年限/部门加成与 ±6 抖动。
> 后果：**60 低于可达最小值，该档永不触发（死代码）；80 只在 0.32% 的抽取中触发** ——
> 整个机制对 99.68% 的用户是惰性的。更根本的是，该机制的设计目的（防止「四维全大吉
> + 小凶签」自相矛盾）在此配置下**结构上不可能发生**：因公平性归一，任何星座都不可能
> 有四维同时 ≥80（实测 0 次 / 8,225,568）。
> 现按实测分布重标定为 **77 / 70**，三档占比 **7.41% / 83.13% / 9.46%**
> —— 低档比高档略多，这是结构性的（加成和接近 0 的画像中心在 70、够不到 77），
> 机制因此对约 17% 的用户产生实际影响，而非原先的 0.3%。
> **统计占比必须用未取整的均分** —— `pickLevel` 收到的是原始浮点值，avg 76.9 属基准档、
> 77.0 才进高档；先四舍五入再分桶会得出 10.7% / 82.9% / 6.4% 的偏差数字。
> **凡调整 `scoring.json` 的 `jitter` 或加成幅度，必须重跑测量并重标定本阈值。**

**纯独立随机被否决**：会出现"四维全大吉 + 小凶签"的直接矛盾，用户立刻判定"不准"。

### 7.2 身份标签的部门过滤

`identity.json` 每条含可选 `dept` 字段（`null` 表示通用）。抽取池 = `本部门专属标签 + 全部通用标签`，再随机。

```json
[
  { "text": "会议隐身术大师", "dept": null },
  { "text": "需求翻译官",     "dept": "tech" },
  { "text": "PRD 措辞艺术家", "dept": "product" }
]
```

纯随机被否决：技术同学抽到"销售话术大师"会立刻出戏。

### 7.3 文案处理

- **插值变量**：`{name}` `{dept}` `{zodiac}` `{tenure}`
- **转义安全**：渲染走 Vue 的 `{{ }}`（自动 HTML 转义），海报走 `ctx.fillText`（不解析 HTML）。**两条路径均不经过 `innerHTML`**，XSS 从结构上不可能发生
- **去重**：`copyEngine.pick(pool, n)` 内部洗牌后切片，保证同次 reading 内不重复取用同一条
- **随机源注入**：`makeRng(seed)` 传入所有抽取函数，单测固定种子即可断言，无需 mock 全局 `Math.random`

## 八、结果页信息架构

### 8.1 locked / unlocked 两态

| 模块 | locked | unlocked |
|---|---|---|
| A 职场身份标签 | **完整露出** | 完整 |

## 十、海报生成

### 10.1 为什么用纯 Canvas 自绘（而非 PRD 推荐的 html2canvas）

海报元素是固定的 6 样结构化数据：背景、姓名、身份标签、四维雷达图、签文、二维码。其中**雷达图本就必须用 Canvas 绘制**，html2canvas 反而要把它再截一次图。无任何照片类素材需要处理。

收益：
- PRD 10 章列出的 5 个已知坑（模糊 / 跨域空白 / 图片未加载完 / 滚动偏移 / 背景图）**一个都不会遇到**
- 省去 html2canvas 约 45KB gzip，对 500KB 红线与弱网均有意义
- 断网绝对可用（无外部图片资源）
- 导出为 `dataURL`，微信内长按保存与转发最稳

代价与缓解：版式靠坐标写、不能用 CSS 调。缓解方式是把坐标、字号、配色全部放进 `config/poster.json`，改版式只改 JSON。

### 10.2 尺寸与布局

固定 **750 × 1334**（2:3 竖版，微信分享标准比例）。自上而下：

```
元素                                    起始 y    占用高度
烫金标题（取 `settings.displayTitle`）      70       42
副标题「打工人能量图鉴」                  112      24
姓名（字号随字数自适应）                  215      70
身份标签（烫金描边圆角卡片）              300      70
四维雷达图                                410      300
四维数值行「摸鱼 72 · 升职 55 · …」       750      30
签文卡片（档位 / 签辞 / 宜 / 忌）          815      230
二维码（白底圆角）                        1080     140
「扫码算你的职场运势」                    1245     24
免责声明（两行）                          1280     48
```

底部余量 6px。**约束**：全部元素须落在 1334 高度内，且底部保留 ≥ 16px 安全边距 —— 精确坐标存 `config/poster.json`，实现时按此约束微调。免责声明全文较长（44 字），18px 字号下必然折为两行，不可压缩为单行。

### 10.3 五个必须处理的技术点

1. **中文字体只能靠系统，版式必须自适应。** Canvas 无法内嵌中文字体（单个字重 3MB+，直接撞破 500KB 红线），只能用 `"PingFang SC", "HarmonyOS Sans", "Microsoft YaHei", sans-serif` 兜底。不同机型字宽不同，因此：
   - 姓名按字数动态降字号：1-3 字 64px / 4-5 字 52px / 6-8 字 42px
   - 所有文案先 `measureText` 量宽，超框自动换行（中文按字累加宽度，不按空格）
   - 身份标签、签辞等变长内容测量后仍溢出则再降一档字号

2. **星空背景用固定种子生成。** 星点坐标由 `makeRng(20260913)` 产出，每次进海报页完全一致。否则用户从海报页返回再进入时星空重排，观感如"图片在闪"。

3. **不使用 `ctx.roundRect`。** 需 Chrome 99+ / Safari 16+，微信 XWeb 内核版本不可控。自写 12 行 `roundRect()` 路径函数，全平台一致。

4. **导出走 `<img src="dataURL">`，不直接显示 canvas。** 微信内**长按 `<img>` 会弹出"保存图片"，长按 `<canvas>` 不一定有**。流程：屏幕外 canvas 绘制 → `toDataURL` → 塞入 `<img>` 显示。

5. **导出格式自适应。** 先试 PNG；若 `dataURL.length` 超过约 1.2MB（深色渐变 + 星点在 PNG 下压缩率差），自动重画为 JPEG 0.92。宁可略有噪点，也不要微信转发时被压糊。

### 10.4 二维码

`qrcode-generator` 输出模块矩阵，逐格 `fillRect` 绘入海报 Canvas 的 140×140 白底圆角区域。指向 `posterBaseUrl`（默认运行时取当前域名）。无需网络。

### 10.5 降级兜底（PRD 11.2 硬要求）

```js
try {
  poster.render()            // 屏幕外 canvas 绘制
  img.src = poster.export()  // PNG 或 JPEG
} catch (e) {
  fallbackToTextMode()       // 纯文字结果页 + 复制链接按钮
}
```

触发条件：canvas 构造失败、字体测量异常、`toDataURL` 抛异常（部分 WebView 对 canvas 有隐性上限）。

**兜底态是一个完整可读的结果页，不是错误提示** —— 用户不能因为一张图崩掉而拿不到完整结果。主流程（看结果、复制链接分享）依旧可用。

| PRD 要求 | 实现方式 |
|---|---|
| 数据不上传服务器 | 零网络请求；无 fetch/XHR/WebSocket；无埋点 SDK |
| 最小必要 | 仅 4 个字段，无手机号/授权/头像/精确生日/照片 |

### 11.1 文案合规 linter（`scripts/lint-copy.js`）

挂载为 `npm run build` 前置，命中即**构建失败**：

- **负面预言黑名单**：破财 / 破产 / 失业 / 被裁 / 裁员 / 生病 / 疾病 / 官司 / 口舌 / 车祸 / 死亡 / 血光 / 离婚 / 分手
- **迷信话术黑名单**：算命 / 占卜 / 改运 / **改命** / 命理 / 前世 / 因果 / 化解 / 生辰八字
  - `改命` 与 `改运` **两个词都收**：PRD 6.2 逐字点名的清单是「不用"命理/运势/前世/因果/化解/**改命**"」，
    而 PRD 8.7 的措辞是「算命/占卜/改运」。二者只有一字之差，语义上都是「用超自然手段改变人生走向」，
    且 `改命` 常作为 `改运` 的近义替换出现在文案里 —— 只收其一等于给替换词留门。
    清单以 `src/config/lint-rules.json` 为**唯一来源**，本节与实现不得各写一套。
  - **不再有例外词**：早期版本为「工位风水」留了 `allowedPhrases` 例外，实测证明其唯一可达效果是
    **跨越切口制造假阳性**（`破工位风水财` 掩码后变成「破财」），而 23 个禁用词中没有任何一个与
    「工位风水」字符重叠 —— 即该例外不能抑制真命中、只能制造误报，且它的两条测试都无法失败。
    已整体移除。PRD 6.2 本就未把「风水」列为禁用词，附录 A 自身以「工位风水研究员」为正面示例。
- **匹配前统一去掉全部空白**：字间距在本项目里是通用约定（`填 4 个空，摇一支签`、`解 锁`、`开 始`），
  不只出现在模板中。**JSON 文案路径与模板路径必须用同一套压缩规则**，否则承载绝大多数用户可见
  文案的 JSON 路径会留一条逃逸通道（`"占 卜"` 绕过全部检查，而用户读到的是「占卜」）。
  长度检查仍按**原始**文本计 —— 空格确实占版面。
- **长度**：单条 > 60 字报错（PRD 6.2）
- **占位符检测**：命中 `【待填写` 时**中止构建（exit 1）**，而非打警告。
  - **早期版本写的是「打警告但不中断」，那是错的**，与本节其余部分以及实现相矛盾。
  - 升级为阻断的理由：`IntroView` 用 `isPlaceholder()` 把占位符挡在渲染之外，所以漏填
    **不会在页面上显形** —— 它会**静默**地让开场页缺少公益捐款说明（PRD 8.6 要求明示）。
    一个每次构建都出现、却从不阻止任何事的警告会迅速变成背景噪音；而静默的合规缺失
    没人会发现。把闸门做成阻断式，是让这件事在唯一必然发生的时刻（构建）以不可忽略的方式暴露。
  - 配套：Task 18 有一步「上线闸门」，会再次检查并明确给出「不可上线」结论。

### 11.2 活动名 vs 页面措辞（重要）

活动本名是「职场算命」，但 PRD 8.7 明确要求页面措辞不得宣称"算命/占卜/改运"。二者冲突，按以下规则处理：

| 场景 | 用词 |
|---|---|
| 易拉宝、桌牌、摊主话术卡（线下物料，不在本工程内） | 「职场算命」 |
| **页面内一切文字**（开场页标题、海报标题、按钮、动画文案） | 「职场运势互动」等免责措辞 |
| `copy/ui.json` 与 `poster.json` 中的展示标题 | 由 `settings.json#displayTitle` 提供，默认「职场运势互动」 |
| 本设计文档、目录名、代码注释（不面向用户） | 「职场算命」 |

因此 `scripts/lint-copy.js` 的扫描范围**必须包含 `copy/ui.json`** —— 它正是页面文案所在。若有人把开场页标题改回「职场算命」，构建会失败，这是预期行为。

### 13.2 开发脚本

- **`node scripts/simulate.js`** — 打印 10000 次抽样的四维等级带分布。调权重时即时查看，不靠感觉。
- **`/debug/poster`（仅 dev 构建）** — 并排渲染 12 种极端输入的海报（1 字姓名 / 8 字全角姓名 / 最长身份标签 / 最低分 / 最高分 / 长签辞等），人眼扫查溢出变形。生产构建由 `import.meta.env.DEV` 摇除。

### 13.3 手工验收（对应 PRD 第十三章）

- **离线验证**（必做）：`npm run build` → `npx serve dist` → **完整加载页面** → DevTools 勾 Offline → **不刷新**，走完整流程（开场页 → 填表 → 摇签 → 结果页）
  - **判定依据是 PRD 第十三章的原文**：「离线后**已加载页面**仍可正常算 + 生成海报」。本节此前写作「勾 Offline → **刷新** → 走完整流程」，那是把验收标准写得比 PRD 更严，且**在本架构下并非目标**（见下）。PRD 同时把下拉刷新列为用户**不应**做的手势（「结果页禁止下拉刷新误触」）。
  - 实测结论（Task 18 核验，可复现）：页面常驻内存时切到 Offline，可完整重走一遍 填表 → 摇签 → 结果页，全程无报错（纯本地计算，无网络依赖）；断网**刷新**则导航失败（`net::ERR_INTERNET_DISCONNECTED`），落到浏览器断网页。
  - **由此接受的残余风险**：产物中**没有 Service Worker**（`dist/` 仅 index.html + JS + CSS；`navigator.serviceWorker.controller === false`、`caches.keys()` 为空），故断网刷新只能靠 HTTP 缓存回源校验，校验失败即整页失败。**现场 WiFi 不稳时，参会者一旦下拉刷新就会卡在断网页，且没有任何提示或兜底。**
  - 接受该风险的三条理由：① PRD 要求的形态（页面常驻时离线可用）**已实测达成**；② 下拉刷新正是 PRD 要求禁止的误触手势，页面已用 `overscroll-behavior-y: none` + `touch-action: manipulation` 抑制（`src/styles/theme.css`），但这只降低概率、不构成保证（各引擎行为不一致，iOS Safari 尤甚）；③ 加 Service Worker 会引入缓存版本管理这一**新的失效面**（旧缓存导致用户长期看到旧版本），收益与风险不匹配 —— **明确划入计划二范围，本次不做**。
  - 因此本步骤的通过标准是：**「已加载页面在断网下仍可完整走完流程」= 通过**；「断网刷新后仍可用」**不在本次验收范围内**，其缺失已如实记入 Task 18 执行记录。
- **零上报验证**（必做）：Network 面板确认除静态资源外无任何外发请求
- **真机走查**：iOS Safari / 微信 XWeb / Android Chrome 各一次，覆盖海报长按保存、转发、口令解锁
